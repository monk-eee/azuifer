# ADR-0011: Compose authentication from shared primitives

- **Status:** Proposed

## Context

Clients use Shared Key, Shared Key Lite, account and service SAS, user-delegation SAS, bearer tokens, and anonymous access. Each service builds a different string-to-sign, and SAS fields and permissions differ per service and API version. The current code verifies only Blob Shared Key and rejects any `sig` parameter.

## Decision and scope

Keep one authentication module that owns the service-independent parts: key lookup for one or two account keys, HMAC-SHA256 verification with constant-time comparison, signature and date-skew checks, SAS field parsing into typed values (`SasPermissions`, start, expiry, IP range, protocol, resource, signed version), and bearer-token validation against locally configured keys or JWKS. Each service supplies a function that builds its canonical string-to-sign for each scheme and states the permission an operation needs. Authentication runs after the resource and operation are parsed, so authorization compares typed required and granted permissions. Anonymous access is granted only where a container's public-access setting allows it. Reduced-validation bearer mode stays off unless explicitly enabled and requires loopback binding. Diagnostics never include signatures, SAS tokens, or full `Authorization` headers.

## Alternatives and consequences

Per-service copies of the signing code duplicate security-sensitive logic. One generic string-to-sign hides real differences between Blob, Queue, Table, and Files. Sharing the primitives and splitting the canonicalization keeps the sensitive comparison in one place at the cost of a function per service and scheme.

## Verification criteria

- Unit tests use Microsoft's published Shared Key, Shared Key Lite, and SAS examples for each service and signed version supported.
- Each service accepts a SAS generated by an official SDK and rejects expired, not-yet-valid, wrong-resource, wrong-permission, and tampered tokens with the Azure error code.
- Either of two configured keys validates; removing a key invalidates tokens signed with it.
- Log capture shows no credential material for failed and successful requests.
