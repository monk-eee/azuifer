# Blob wire compatibility

Use the [quick start](../../README.md#run-locally) with the Blob API version `2023-11-03`. [The manifest](../../specs/conformance/blob.json) lists supported operations, authorization modes, and known differences. No operation is rated `exact`. The [Azure cassette suite](azure-contracts.md) records the specific behavior checked against live Azure.

This slice covers block, page, and append blobs, with snapshots, versions, and soft delete of all three types, blob index tags, Set Blob Expiry, immutability policies and legal holds, soft-deleted containers, incremental copy, opt-in copies from external URLs, and Submit Batch. DFS is separate work.

## Operations

Anything else, including unsupported query parameters and `x-ms-*` headers, answers an Azure-shaped `NotImplemented` error instead of being ignored. Rename Container (not a public Azure operation) is not implemented. Query Blob Contents is a SQL subset over delimited text and JSON ([ADR-0027](../adr.d/0027-query-blob-contents-with-a-small-sql-subset.md)); Arrow and Parquet answer `NotImplemented`.

### Page blobs and append blobs

Page and append blob content is a map from blob offsets to immutable extents ([ADR-0015](../adr.d/0015-map-mutable-ranges-over-immutable-extents.md)). Every write streams into a new extent, is made durable, and then commits its range rows and new ETag in one metadata transaction ([ADR-0004](../adr.d/0004-commit-durable-content-references.md)), so a crash exposes the previous content or the whole new write. Clearing and shrinking change rows only, unwritten ranges allocate nothing, and extents are deleted when no blob references them. Startup recovery keeps referenced extents and removes staging files and orphans.

- **Create.** `Put Blob` with `x-ms-blob-type: PageBlob` requires `x-ms-blob-content-length` (a multiple of 512 up to 8 TiB) and accepts `x-ms-blob-sequence-number` and a premium `x-ms-access-tier` (`P4` to `P80`). `AppendBlob` creates an empty blob. Both need `Content-Length: 0`, replace any blob of the same name (and so change its type) subject to the usual conditions and lease, and discard uncommitted blocks.
- **Put Page.** `x-ms-page-write: update` writes up to 4 MiB at a 512-aligned `x-ms-range` or `Range` and accepts `Content-MD5` or `x-ms-content-crc64`. `clear` takes `Content-Length: 0` and any aligned range. `x-ms-if-sequence-number-le`, `-lt`, and `-eq` must all hold or the answer is 412 `SequenceNumberConditionNotMet`. A misaligned or out-of-bounds range is 416 `InvalidPageRange`. Responses carry `x-ms-blob-sequence-number`.
- **Get Page Ranges.** `GET comp=pagelist` lists allocated ranges, optionally inside an `x-ms-range` or `Range` window, with `maxresults` and `marker` paging through `NextMarker`. Touching allocated ranges are reported as one range. `snapshot` lists the ranges of one snapshot, and `prevsnapshot` (with the live blob or a newer `snapshot` as the target) answers the diff Azure calls Get Page Ranges Diff: `PageRange` elements for ranges that were written or changed since the earlier snapshot and `ClearRange` elements for ranges that were allocated then and are not now (a shrunk blob reports its trailing ranges as cleared), in offset order. A `prevsnapshot` newer than the target is 400 `PreviousSnapshotCannotBeNewer`, one that does not exist (or is not a page blob snapshot) is 409 `PreviousSnapshotNotFound`, and a missing `snapshot` is 404 `BlobNotFound`. The diff compares extents, so it is exact; a range rewritten with identical bytes still counts as changed, as in Azure. The window, `maxresults`, and `marker` apply to changed and cleared ranges together.
- **Resize and sequence number.** Set Blob Properties with `x-ms-blob-content-length` resizes (shrinking discards trailing data, growing adds a hole). `x-ms-sequence-number-action` is `max`, `update`, or `increment` with `x-ms-blob-sequence-number` for the first two. Either can accompany content properties.
- **Append Block.** Up to 100 MiB (4 MiB before API version 2022-11-02; AzCopy sends 8 MiB blocks) and 50,000 blocks, with `Content-MD5` or crc64, `x-ms-blob-condition-maxsize` (412 `MaxBlobSizeConditionNotMet`), and `x-ms-blob-condition-appendpos` (412 `AppendPositionConditionNotMet`). The 201 response reports `x-ms-blob-append-offset` and `x-ms-blob-committed-block-count`. The 50,001st block is 409 `BlockCountExceedsLimit`. Zero-length blocks are rejected.
- **Seal.** `PUT comp=seal` (optionally with `x-ms-blob-condition-appendpos`) makes an append blob read-only: later appends are 409 `BlobIsSealed`, while metadata changes and delete still work. Sealing a sealed blob changes nothing.
- **Reads and listings.** Get Blob streams page blob holes as zeros and returns an append blob as its concatenated blocks, both with range support. Get and Head report `x-ms-blob-type`, `x-ms-blob-sequence-number` (page), and `x-ms-blob-committed-block-count` and `x-ms-blob-sealed` (append, sealed only when true). List Blobs reports `BlobType`, `Content-Length` (the logical length), `x-ms-blob-sequence-number`, and `Sealed`. Page blobs show an access tier only after one was set, and the tiers `P4` to `P80` are accepted only on page blobs.
- **Wrong blob type.** Put Block, Put Block List, and Get Block List on a page or append blob, Put Page, Get Page Ranges, resize, and sequence changes on other types, and Append Block and Seal on other types answer 409 `InvalidBlobType`.
- **From URL and copy.** Put Page From URL and Append Block From URL read a range of a same-instance source with the same authorization as Copy Blob; Put Page From URL needs `x-ms-source-range` and a `Content-Length: 0` request. Copy Blob of a page or append blob (or of one of its snapshots or versions, including promoting a version onto the blob name) keeps the type, sequence number, and committed block count, shares the source's extents (so holes stay holes), and leaves the copy unsealed. `x-ms-tags` is accepted on Put Blob of page and append blobs.

Snapshots, versions, and soft delete apply to page and append blobs as they do to block blobs (see below): a history row records the blob type, sequence number, and committed block count, and a `history_ranges` table holds the retained range map over the same extents ([ADR-0015](../adr.d/0015-map-mutable-ranges-over-immutable-extents.md), [ADR-0018](../adr.d/0018-model-snapshots-versions-and-copy-as-immutable-references.md)). A snapshot therefore copies rows, never bytes, and an extent is deleted only when no live range row and no history range row references it.

Known differences: `x-ms-source-content-md5` and `x-ms-seal-blob` are not implemented. Put Blob From URL and Put Block From URL accept only block blob destinations, and a page blob source is read densely (holes become zeros), so reading a very large sparse source this way is costly. Premium tiers are stored and reported but do not change behavior. A partly overwritten extent stays allocated until every range using it is replaced, so storage can exceed the live data. With soft delete and no versioning, a Put Page does not retain the overwritten pages (only Put Blob, Put Block List, Copy Blob, and delete do); with versioning each Put Page, Append Block, resize, seal, and property change retires the previous state as a version, which copies the blob's range rows.

### Properties, metadata, conditions

Put Blob and Put Block List store `x-ms-blob-content-type`, `-encoding`, `-language`, `-disposition`, `-cache-control`, and `-md5` (Put Blob also accepts the plain `Content-Type`, `Content-Encoding`, `Content-Language`, `Content-Disposition`, and `Cache-Control`), `x-ms-meta-*`, and `x-ms-access-tier`. Get and Head return them, with creation time, lease, copy, and tier headers. Set Blob Properties replaces all six content properties when any is sent. Metadata names are lowercase: the HTTP layer folds header case, so `x-ms-meta-Owner` reads back as `owner`.

`If-Match`, `If-None-Match`, `If-Modified-Since`, and `If-Unmodified-Since` apply to every blob operation (both ETag conditions together too), and the date conditions to container operations. A failed condition answers 304 for reads where Azure does and 412 `ConditionNotMet` otherwise; copy source conditions answer `SourceConditionNotMet`. `If-None-Match: *` on an existing blob is 409 `BlobAlreadyExists` for Put Blob and Put Block List. Range reads take one `bytes=start-end` range, and `x-ms-range-get-content-md5` or `-crc64` returns the checksum of ranges up to 4 MiB.

### Listings

List Blobs supports `prefix`, `delimiter` (with `BlobPrefix` entries), `maxresults`, opaque `marker` tokens, and `include=metadata,copy,uncommittedblobs,snapshots,versions,deleted,tags`. Pages count blobs and prefixes together, and a marker after a collapsed prefix skips everything under it. Other `include` values answer `NotImplemented`, as does combining `uncommittedblobs` with `snapshots`, `versions`, `deleted`, or `tags`. Within one name the listing returns snapshots and versions oldest first and the current blob last. `Snapshot`, `VersionId`, `IsCurrentVersion`, `Deleted`, `DeletedTime`, `RemainingRetentionDays`, and, with `include=tags`, `TagCount` and `Tags` appear where Azure puts them.

### Snapshots

Snapshot Blob (`PUT comp=snapshot`) answers 201 with `x-ms-snapshot` (a `YYYY-MM-DDThh:mm:ss.fffffffZ` time), the base blob's ETag and `Last-Modified`, and `x-ms-version-id` when the account keeps versions. Any `x-ms-meta-*` header replaces the copied metadata; `If-Match`-style conditions, `x-ms-if-tags`, and `x-ms-lease-id` are checked against the base blob, and a snapshot of a leased blob does not need the lease id. A snapshot keeps the blob's content, content properties, metadata, ETag, and block list (or, for a page or append blob, its type, sequence number, committed block count, and range map). On disk it shares the blob's immutable extent instead of copying bytes ([ADR-0018](../adr.d/0018-model-snapshots-versions-and-copy-as-immutable-references.md)): an extent is deleted only when no blob, snapshot, version, soft-deleted entry, history range row, or staged block references it, and startup recovery keeps every referenced extent. The in-memory backend copies block blob bytes and counts them against `--memory-limit`; page and append extents are shared there too and counted once.

`GET`, `HEAD`, `comp=metadata`, `comp=blocklist`, and `comp=pagelist` accept `snapshot=…`; a missing snapshot is 404 `BlobNotFound` and a malformed one is 400 `InvalidQueryParameterValue`. `snapshot` and `versionid` together are rejected. Delete Blob refuses a blob that has snapshots with 409 `SnapshotsPresent` unless `x-ms-delete-snapshots` is `include` (delete the blob and its snapshots) or `only` (delete just the snapshots); `DELETE ?snapshot=…` removes one snapshot and rejects `x-ms-delete-snapshots`. Delete answers `x-ms-delete-type-permanent`: `true`, or `false` when the data stays as a version or soft-deleted entry. Snapshot sources work in Copy Blob and Put Blob From URL (`?snapshot=…` on the source URL); block blob copies still duplicate bytes, and a Put Blob From URL of a page or append snapshot reads it densely. Set Blob Metadata, Set Blob Properties, and writes do not apply to snapshots, and a snapshot is not a valid target for tags (501).

### Versions

Versioning is an account setting that Azure manages outside the Blob data plane, so Azuifer takes it from configuration: `--versioning-accounts a,b`, `AZUIFER_VERSIONING_ACCOUNTS`, or `versioning_accounts = "a,b"` in the TOML file (each name must be a configured account; the option is applied at every start). For those accounts every write that changes the current blob (Put Blob, Put Block List, Copy Blob, Set Blob Metadata, Set Blob Properties, and for page and append blobs Put Page, Append Block, resize, and seal) assigns a new version id (`x-ms-version-id`, also on Get and Head with `x-ms-is-current-version`) and retires the previous state as a version that shares its extent or range map. `?versionid=…` reads, deletes, and addresses tags of a version; a version id equal to the current one is the current blob. Deleting the current blob keeps every version, so `include=versions` still lists them; Copy Blob from `…?versionid=…` onto the blob name promotes a version, of any blob type. A blob written before versioning was enabled becomes a version, with its last-modified time as id, on its next write. Snapshots do not get version ids, and the version listing does not mark deleted versions separately.

### Soft delete

Set Blob Service Properties `DeleteRetentionPolicy` (`Enabled`, `Days` 1 to 365) turns on soft delete for blobs and for containers (see [Soft-deleted containers](#soft-deleted-containers)). Delete Blob then keeps the blob and the snapshots it deletes as deleted entries for `Days` days from the deletion, measured on the injected clock ([ADR-0012](../adr.d/0012-inject-time-through-one-clock.md)) and checked lazily on each request, so `--test-clock` can expire them. They are invisible to reads and plain listings; `include=deleted` shows them with `Deleted`, `DeletedTime`, and `RemainingRetentionDays`, and Undelete Blob (`PUT comp=undelete`) restores the blob (a page or append blob with its type, sequence number, and ranges), its tags, and the deleted snapshots and versions (200; 404 `BlobNotFound` when nothing was ever there). Undeleting a live blob succeeds and restores only its deleted snapshots. On a hierarchical-namespace account an undelete recreates the missing parent directories and is 409 `BlobOperationNotSupported` when the name has since become a directory or a parent a file. Overwriting a blob (Put Blob, Put Block List, Copy Blob) keeps the old state as a soft-deleted snapshot when versioning is off. With versioning on, a delete keeps a version instead, and deleted snapshots and versions are retained for the same period. The retention applies when the data is deleted; changing the policy later does not affect earlier deletions. Expired entries disappear from every response at once; their storage is reclaimed at startup and by the next delete, snapshot, or undelete.

### Incremental Copy Blob

`PUT {destination}?comp=incrementalcopy` with `x-ms-copy-source` naming a snapshot (`…?snapshot=…`) of a page blob on this instance copies it into the destination page blob. The first copy creates the destination; each later copy must name a newer snapshot of the same source blob and takes only what changed, which here costs nothing extra because the destination shares the snapshot's extents. When a copy finishes the destination takes a snapshot of its own, so `x-ms-copy-destination-snapshot` and `x-ms-incremental-copy: true` appear on Get and Head (`DestinationSnapshot` and `IncrementalCopy` in listings), and Get Page Ranges with `prevsnapshot` diffs the destination's snapshots. The copy completes synchronously: the 202 answer carries `x-ms-copy-status: success` and an `x-ms-copy-id`, never `pending`, and Abort Copy has nothing to abort. Errors: 409 `IncrementalCopySourceMustBeSnapshot` (no `snapshot`), `InvalidSourceBlobType` (a block or append source), `IncrementalCopyBlobMismatch` (another source blob), `IncrementalCopyOfEarlierVersionSnapshotNotAllowed` (an older snapshot than the last one copied), `OperationNotAllowedOnIncrementalCopyBlob` (Put Page on the destination), and `BlobAlreadyExists` (the destination exists and is not an incremental copy blob); a missing source is 404 `CannotVerifyCopySource`. On a hierarchical-namespace account the destination creates its missing parents in the copy's transaction. Sources on another instance or account are not supported.

### Set Blob Expiry

`PUT ?comp=expiry` takes `x-ms-expiry-option` (`RelativeToCreation`, `RelativeToNow`, `Absolute`, or `NeverExpire`, case-insensitive) and `x-ms-expiry-time` (milliseconds for the two relative options, an HTTP date for `Absolute`, none for `NeverExpire`). A deadline that is not in the future is 400 `InvalidHeaderValue`, a missing option or time 400 `MissingRequiredHeader`, and the blob's lease id is required while it has an active lease. The blob answers `x-ms-expiry-time` on Get and Head and `Expiry-Time` in List Blobs. At the deadline, measured on the injected clock ([ADR-0022](../adr.d/0022-keep-blob-lifecycle-state-and-sweep-lazily.md)), the blob and its snapshots are gone: the removal runs before the next metadata request, so every operation, including DFS, sees it as absent at once. Azure does not soft-delete an expired blob and neither does Azuifer; an account that keeps versions keeps the blob as a version. A write that replaces the blob (Put Blob, Put Block List, Copy Blob) starts a new blob without an expiry, and Set Blob Properties and metadata keep it. Known difference: Azure allows Set Blob Expiry only on hierarchical-namespace accounts; Azuifer accepts it on every account.

### Immutability policies and legal holds

`PUT ?comp=immutabilityPolicies` sets a time-based policy from `x-ms-immutability-policy-until-date` (an HTTP date after now) and `x-ms-immutability-policy-mode` (`Unlocked`, the default, or `Locked`); `DELETE ?comp=immutabilityPolicies` removes an unlocked or ended policy; `PUT ?comp=legalhold` with `x-ms-legal-hold: true` or `false` sets or clears a hold. None of them changes the ETag. Get, Head, and List Blobs report `x-ms-immutability-policy-until-date`, `x-ms-immutability-policy-mode`, and `x-ms-legal-hold`. While a legal hold or an unexpired policy applies, Put Blob, Put Block List, Copy Blob onto the blob, Put Page, Append Block, resize, seal, Set Blob Properties and Metadata, and Delete Blob answer 409 `BlobImmutableDueToLegalHold` or `BlobImmutableDueToPolicy`, and so does Delete Container for a container that holds such a blob. Snapshots, Set Blob Tier, tags, leases, and reads are not blocked. A policy may be shortened or replaced while unlocked; once locked it can only be extended, never unlocked, shortened, or deleted until it ends. In an account that keeps versions a write is allowed and leaves the protected state behind as a version, but a delete is still refused. Policies and holds apply to the current blob only: `snapshot=` and an older `versionid` answer `NotImplemented`, a retired version is not itself protected, and container-level immutability policies (and `x-ms-immutable-storage-with-versioning`) are not implemented. The immutability headers on Put Blob (`x-ms-immutability-policy-until-date`, `-mode`, `x-ms-legal-hold`) are not accepted; set them with the operations above. A SAS needs `i` for policies and `i` or `l` for holds.

### Blob index tags

`x-ms-tags` (URL-encoded `key=value` pairs joined by `&`) on Put Blob (of any blob type), Put Block List, Copy Blob, and Put Blob From URL sets the tags of the written blob; a write without it clears the tags. `x-ms-copy-source-tag-option` on Copy Blob and Put Blob From URL is `REPLACE` (the default: the tags are those of `x-ms-tags`) or `COPY` (the tags of the source blob or version; with `x-ms-tags` it is a 409 `InvalidHeaderValue`, and any other value is 400); it applies to block, page, and append copies and not to sources on other hosts, which carry no tags. Set Blob Tags (`PUT comp=tags`, XML `Tags/TagSet/Tag/Key,Value`, 204) and Get Blob Tags (`GET comp=tags`) address the current blob or a version (`versionid`). Azure's limits are enforced: ten tags, 1 to 128 character keys, 0 to 256 character values, letters, digits, space, and `+ - . / : = _`, with 400 `TagsTooLarge` or `InvalidTag`. Get and Head report `x-ms-tag-count`. Tags do not change the ETag. `x-ms-if-tags` (and `x-ms-source-if-tags` on copy sources) is a condition on Get, Head, metadata, properties, Put Blob and Put Block List overwrites, Delete, Snapshot, Lease, Get Block List, and the tag operations; a failed condition is 412 `ConditionNotMet` and a malformed one is 400 `InvalidHeaderValue`. Operations that do not support it, such as Set Blob Tier, answer `NotImplemented` when it is sent.

Find Blobs by Tags (`GET /{account}?comp=blobs&where=…`, or `/{container}?restype=container&comp=blobs&where=…`) takes `"tag" = 'value'` comparisons with `=`, `>`, `>=`, `<`, and `<=` joined by `AND`, plus `@container = 'name'` at account scope. Names are double-quoted and values single-quoted (doubling the quote escapes it); `OR`, parentheses, and other operators are 400 `InvalidQueryParameterValue`. Comparisons are ordinal. Results (`Name`, `ContainerName`, `Tags`) are immediately consistent, cover current blobs only, and page by container then name with `maxresults` and `NextMarker`.

### Submit Batch

`POST /{account}?comp=batch` (or `/{container}?restype=container&comp=batch`) takes a `multipart/mixed` body of at most 256 Delete Blob or Set Blob Tier sub-requests of one kind and answers 202 with a `multipart/mixed` body of one `application/http` part per item, each with its `Content-ID`, status, `x-ms-request-id`, and for failures `x-ms-error-code` and the XML error. Each sub-request is parsed and authenticated on its own through the normal path (Shared Key signature, SAS, or anonymous access) and runs at the batch's API version, so an unauthorized or failing item does not affect the others; the batch request itself needs Shared Key or an account SAS. Sub-requests must address the batch's account (and container, for a container-scoped batch). A malformed, oversized, empty, or mixed-kind batch is 400 `InvalidInput`.

### Leases

Blob and container leases follow [ADR-0017](../adr.d/0017-model-leases-as-a-clocked-state-machine.md): acquire (15 to 60 seconds or `-1`), renew, change, release, and break (period 0 to 60), with `x-ms-lease-state`, `-status`, and `-duration` on Get and Head, container properties, and listings. Every mutating blob operation, Delete Container, and Put Block require `x-ms-lease-id` while a lease is active. Reads, Set Blob Tier, and container metadata or ACL changes accept an optional id that must match. The responses use Azure's codes: `LeaseIdMissing`, `LeaseIdMismatchWithBlobOperation` and `…WithContainerOperation` and `…WithLeaseOperation`, `LeaseNotPresentWith…Operation`, `LeaseAlreadyPresent`, `LeaseLost`, `LeaseIsBreakingAndCannotBeAcquired`, `LeaseIsBreakingAndCannotBeChanged`, and `LeaseIsBrokenAndCannotBeRenewed`. Expiry is evaluated against the clock on each request, and the lease fields persist across restart.

### Soft-deleted containers

With a `DeleteRetentionPolicy` on the account (the one setting also governs blob soft delete, where Azure keeps a separate container setting in the management plane), Delete Container keeps the container and everything in it under a hidden name for `Days` days on the injected clock instead of deleting it: blobs, snapshots, versions, tags, metadata, and the ACL stay, and the lease is cleared. The name is free at once. `GET comp=list&include=deleted` (alone or with `metadata`) lists deleted containers with `Deleted`, `Version`, `DeletedTime`, and `RemainingRetentionDays`. Restore Container, `PUT /{destination}?restype=container&comp=undelete` with `x-ms-deleted-container-name` and `x-ms-deleted-container-version`, renames the deleted container to the destination name and answers 201; the destination may differ from the deleted name, and one that exists is 409 `ContainerAlreadyExists`. An unknown or expired version is 404 `ContainerNotFound`. Hidden containers are invisible to listings, tag searches, and every other operation, and expired ones are erased (their extents too) before the next metadata request. With no retention policy, Delete Container is permanent as before. A container that holds a legal hold or an unexpired immutability policy cannot be deleted at all.

### Copy

Copy Blob, Put Blob From URL, and Put Block From URL accept **same-instance sources**: a path-style (`http://127.0.0.1:10000/{account}/…`) or host-style URL on this listener. Copies complete synchronously with `x-ms-copy-status: success` and an `x-ms-copy-id`, so Abort Copy always answers `NoPendingCopyOperation` (or `CopyIdMismatch`). The source is readable with the caller's Shared Key inside the same account, with a read SAS on the source URL, or through public access; otherwise the request answers 403 `CannotVerifyCopySource`. Copies of block blobs still duplicate the bytes; page and append blob copies share extents (see above), and snapshots, versions, and soft-deleted entries share extents ([ADR-0018](../adr.d/0018-model-snapshots-versions-and-copy-as-immutable-references.md)). Note that `az storage blob copy start --source-blob` builds a `core.windows.net` source URL, so use `--source-uri` with the local URL.

**External sources (opt-in, [ADR-0024](../adr.d/0024-fetch-external-copy-sources-only-from-allowlisted-hosts.md)).** A source URL on any other host answers `NotImplemented` unless the operator lists the host with `--allow-external-copy-sources host,host:port,*.domain` (`AZUIFER_ALLOW_EXTERNAL_COPY_SOURCES`, `allow_external_copy_sources` in TOML; empty by default). Copy Blob, Put Blob From URL, Put Block From URL, Append Block From URL, and Put Page From URL then fetch the source over HTTP(S) with `reqwest` (rustls) and stream it into the normal upload path, so the destination rules, quotas, and Blob/DFS invariants are those of any other write. The fetch is guarded against server-side request forgery: only listed hosts are contacted; a loopback, private, link-local (including `169.254.169.254`), shared-range, documentation, multicast, or otherwise non-public address is refused unless the operator named that exact host or address (a `*.domain` entry accepts only hosts that resolve to public addresses only, and refusing one private answer refuses the host); the address that passed the check is the one connected to, so a second DNS answer cannot redirect it; redirects are never followed (403 `CannotVerifyCopySource`); `x-ms-source-range` becomes a `Range` request; the response must announce its length and stay under `--max-assembled-blob-bytes` (413 `RequestBodyTooLarge`); connect and total times are bounded (10 seconds to connect, `--upload-timeout-seconds` overall); and a URL with user information is 400. A SAS in the source URL is passed to the source and never logged or recorded: `x-ms-copy-source` on the destination shows the URL without its query. The destination takes the source's content headers (`Content-Type`, `Content-Encoding`, `Content-Language`, `Content-Disposition`, `Cache-Control`) and no metadata or tags. Source conditions (`x-ms-source-if-*`) and `x-ms-source-lease-id` are `NotImplemented` for these sources. Known difference: Azure copies from an external URL asynchronously (`x-ms-copy-status: pending`); Azuifer completes the copy before answering, as for same-instance sources, and a failure answers the request instead of a failed copy status.

## Authentication

Requests authenticate with Shared Key, Shared Key Lite, an account SAS, a service SAS on a blob or container (`sr=b` or `sr=c`), or anonymously where public access allows ([ADR-0011](../adr.d/0011-compose-authentication-from-shared-primitives.md), [ADR-0019](../adr.d/0019-store-account-level-blob-features-separately.md)).

- SAS strings-to-sign follow signed versions 2015-04-05 through 2023-11-03, including the 2018-11-09 resource fields and the 2020-12-06 encryption scope. Permissions `r a c w d x y l t f m e o p` are accepted; each operation names the letters it needs, and a `c`-only SAS can also overwrite on Put Blob. Stored access policies (`si`) supply permissions and times from the container ACL. `rscc`, `rscd`, `rsce`, `rscl`, and `rsct` override Get Blob headers. Account SAS checks `ss`, `srt`, and `sp`.
- Errors use Azure's codes: `AuthenticationFailed` for signature, window, and resource mismatches, `AuthorizationPermissionMismatch`, `AuthorizationResourceTypeMismatch`, `AuthorizationServiceMismatch`, and `AuthorizationProtocolMismatch` (`spr=https` on a plain-HTTP listener; with TLS enabled, `spr=https` matches).
- `sip` is parsed but not enforced: the listener does not expose the client address to the router. A user-delegation SAS (`skoid`) is validated as described under [User-delegation SAS](#user-delegation-sas).
- A container's public access level (`x-ms-blob-public-access`, stored with its ACL) allows anonymous Get Blob, Get Blob Properties and Metadata, and Get Block List at `blob` level, and also List Blobs and Get Container Properties and Metadata at `container` level. A blocked anonymous blob read answers 404 `ResourceNotFound`; other blocked requests answer 403.
- `x-ms-version` is required on Shared Key requests and optional with SAS or anonymous access. Every version from 2009-09-19 up to the baseline is served with baseline behavior, as older SDKs and `az` send them; `--skip-api-version-check` additionally lets a client that sends a newer well-formed version use the baseline. The response reports the effective version. `x-ms-client-request-id` is echoed.

### TLS

Every service listener (Blob, Queue, Table, DFS, and File) serves HTTPS when a certificate is configured, with one certificate shared by all of them. The administration listener (`/healthz`, `/readyz`) stays plain HTTP so probes need no trust store. The `blob_url=`, `queue_url=`, and other startup lines print `https://` addresses, and listing and OData URLs use the same scheme. The stack is rustls with the `ring` provider, so no system OpenSSL is needed on Windows, macOS, or Linux.

| Source | Flag | Environment | TOML (`[tls]`) |
| --- | --- | --- | --- |
| PEM certificate chain and key | `--tls-cert <file> --tls-key <file>` | `AZUIFER_TLS_CERT`, `AZUIFER_TLS_KEY` | `cert`, `key` |
| PKCS#12 | `--tls-pfx <file> [--tls-pfx-password <pw>]` | `AZUIFER_TLS_PFX`, `AZUIFER_TLS_PFX_PASSWORD` | `pfx`, `pfx_password` |
| Generated development certificate | `--tls-generate` | `AZUIFER_TLS_GENERATE` | `generate` |

Choose one source. `--tls-generate` creates a self-signed ECDSA P-256 certificate for `localhost`, `127.0.0.1`, `::1`, and `*.blob.localhost`, `*.queue.localhost`, `*.table.localhost`, `*.dfs.localhost`, and `*.file.localhost`. It writes `azuifer-dev.crt` and `azuifer-dev.key` under `<location>/tls/` and reuses them on later runs (delete the directory to regenerate). With `--in-memory` it writes to a temporary directory that is removed at shutdown. Either way startup prints `tls_cert=<path>`, the file to trust: set `REQUESTS_CA_BUNDLE` (Azure CLI and the Python SDKs), `connection_verify=<path>` on an SDK client, `NODE_EXTRA_CA_CERTS`, or `SSL_CERT_FILE`, or import it into the operating system trust store. A password-protected PFX from OpenSSL (AES) or Windows (3DES) loads; the PFX password is not logged. A non-loopback bind still needs `--bind` and a custom Shared Key as before.

### Bearer tokens (OAuth)

`Authorization: Bearer <JWT>` works on every service. Azure SDKs send bearer tokens only over HTTPS, so enable TLS to use them from an SDK.

| `--oauth` (`AZUIFER_OAUTH`, TOML `[oauth] mode`) | Behavior |
| --- | --- |
| `off` (default) | A bearer token is rejected with 401 `InvalidAuthenticationInfo` and a `WWW-Authenticate: Bearer authorization_uri=… resource_id=https://storage.azure.com` challenge (DFS reports 403 `AuthorizationFailure`, its own error shape). |
| `basic` | Reduced validation, like Azurite: the token must be a well-formed JWT with an Entra issuer (`https://sts.windows.net/{tenant}/` or `https://login.microsoftonline.com/{tenant}/v2.0`), a storage audience, and a valid `exp` and `nbf` (five minutes of skew, against the service clock). **The signature is not verified**, so an unsigned test token works. It is refused with a non-loopback bind and is a controlled-local-test mode, not a deployment mode. Every operation is allowed. |
| `jwks` | Verifies RS256 signatures against `--oauth-jwks <file or https URL>` (`AZUIFER_OAUTH_JWKS`, `jwks`), and requires `--oauth-issuer` (`AZUIFER_OAUTH_ISSUER`, `issuer`; comma-separated) and optionally `--oauth-audience` (`AZUIFER_OAUTH_AUDIENCE`, `audience`; comma-separated). A JWKS that cannot be read stops startup. A URL is refetched hourly and a failed refresh keeps the old keys; `http://` URLs are accepted only for loopback. Other algorithms, including `none` and HS256, are rejected. |

Accepted audiences in `basic` mode (and in `jwks` mode without `--oauth-audience`) are `https://storage.azure.com` (with or without a trailing slash), `https://{account}.{blob,queue,table,dfs,file}.core.windows.net`, and the address the client used (`https://{host}` or `https://{host}/{account}`). Authorization is deliberately coarse. In `jwks` mode a token with a `roles` claim is limited to the Azure data roles it names: `Storage Blob Data Owner`, `Contributor`, or `Reader` for Blob and DFS, `Storage Queue Data Contributor` or `Reader`, `Storage Table Data Contributor` or `Reader`, and `Storage File Data Privileged Contributor`, `Privileged Reader`, or `SMB Share Contributor`, `Elevated Contributor`, or `Reader` for Files. A Reader role may only issue `GET`, `HEAD`, and `OPTIONS`; a writer role may do anything; any other role on that service gets 403 `AuthorizationPermissionMismatch`. A `jwks` token without a `roles` claim, and every `basic` token, is allowed everything. Azure RBAC role assignments and POSIX ACLs are not modeled. Azure Files does not require `x-ms-file-request-intent`.

### User-delegation SAS

`POST /{account}?restype=service&comp=userdelegationkey` (Get User Delegation Key) needs a bearer token; Shared Key, SAS, and anonymous callers get 403. The body is `<KeyInfo><Start>…</Start><Expiry>…</Expiry></KeyInfo>` with `Start` optional (default now) and `Expiry` at most seven days after it. The reply carries a random 32-byte `Value`, `SignedOid` and `SignedTid` from the token's `oid` and `tid` claims (all zeros when absent), the window, `SignedService` `b`, and the baseline `SignedVersion`. Keys are held in memory, so a restart invalidates every user-delegation SAS. For missing expiry, malformed start, and a future expiry before start, the [live Azure comparison](azure-contracts.md) verifies `400 InvalidXmlNodeValue`, the specific XML node and value, and a matching request ID in the error message.

A SAS with `skoid`, `sktid`, `skt`, `ske`, `sks=b`, and `skv` is verified against the issued key. The string-to-sign follows the documented layouts for signed versions 2018-11-09 and later (including the 2020-02-10 snapshot time, the 2020-12-06 encryption scope, and the 2025-07-05 and 2026-04-06 additions), for `sr=b`, `c`, `bs`, and `bv`. The SAS fails once its own window or its key's window has ended. `saoid`, `suoid`, and `scid` are signed but not acted on. A stored access policy (`si`) is refused, as in Azure; the user-bound and request-constraint fields `sduoid`, `skdutid`, `srh`, and `srq` answer `NotImplemented`. The permissions are exactly the SAS's `sp`: the intersection with the key owner's RBAC permissions is not modeled. User-delegation SAS exists for Blob only; DFS, Queue, Table, and Files reject it.

## Service properties and CORS

Service properties (logging, metrics, CORS rules, default service version, delete retention, static website) are stored per account and returned on request, with Azure's defaults for a new account; an update changes only the elements it contains. CORS is acted on: `OPTIONS` preflights and requests with an `Origin` header are matched against the rules at the HTTP edge. `DeleteRetentionPolicy` drives blob and container soft delete. The static website setting is served ([ADR-0025](../adr.d/0025-serve-the-static-website-from-the-web-host.md)): the `$web` container can be created, and `GET` and `HEAD` on the host `{account}.web.{domain}` (for example `http://devstoreaccount1.web.localhost:10000/`) read it anonymously. An empty path or one ending in `/` returns that directory's index document, a directory path without the slash answers 302, and a missing path returns the 404 document with status 404 (otherwise an HTML 404 with `x-ms-error-code: WebContentNotFound`). A disabled website, an unknown account and other methods answer 404 and 405. `defaultIndexDocumentPath`, custom domains and Azure's `z13` host form are not served, and the HTML bodies only approximate Azure's. `$root` and `$logs` are ordinary containers that clients create; a request for a single path segment without `restype=container` (for example `GET /{account}/blob.txt`) addresses a blob in `$root` ([ADR-0028](../adr.d/0028-address-the-root-container-by-a-single-path-segment.md)), and Azuifer writes no analytics logs into `$logs`. Get Account Information returns fixed, correctly shaped values. Get Blob Service Stats answers a fixed `live` geo-replication shape only on the read-only secondary endpoint, the host-style `http://{account}-secondary.blob.localhost:{port}/` (Azure's `{account}-secondary` host form, which also resolves the account for any other request on it); on the primary endpoint it is 403 `InsufficientAccountPermissions`, as Azure answers for an account without a secondary. The path-style `/{account}-secondary` form that Azurite uses is not supported, and the Python SDK builds its secondary host name from `core.windows.net`, so call the endpoint directly or use a client that accepts a custom secondary host.

## Addressing

Both addressing styles work: `http://127.0.0.1:10000/{account}/{container}/{blob}` and `http://{account}.blob.localhost:10000/{container}/{blob}` (any `{account}.blob.{domain}` host); Queue, Table, Files and DFS accept the same `{account}.{service}.{domain}` form. Shared Key signs the path as sent. `UseDevelopmentStorage=true` resolves to the path-style endpoint of the built-in `devstoreaccount1` account. Python's SDK cannot infer the account from a `.blob.localhost` host, so pass `credential={"account_name": …, "account_key": …}`.

## Storage and configuration

- `serve --location ./data` uses SQLite WAL for metadata and filesystem extents for payloads. Uploads are staged, checked, and synced before publishing the metadata reference. Startup reclaims unreferenced files from interrupted writes. Keep the directory private to one process and use a local filesystem. Opening a directory created by an earlier release adds the new columns and tables with defaults (`PRAGMA user_version`); old blobs keep their ETags, and a container keeps its ETag until it changes.
- Opening a directory also adds the snapshot, version, soft-delete, and tag tables (migration 3 of `PRAGMA user_version`; migrations are keyed by number). Existing blobs have no version id and no tags. Migration 6 adds the blob type columns to the history rows, the `history_ranges` table (range maps of retained page and append blobs), the `blob_lifecycle` table (expiry, immutability policy, legal hold, and incremental copy snapshots per blob), and the `deleted_containers` table; existing data keeps working with no expiry, no protection, and no deleted containers.
- `--allow-external-copy-sources` (`AZUIFER_ALLOW_EXTERNAL_COPY_SOURCES`, `allow_external_copy_sources`) lists the hosts external copy sources may use; see [Copy](#copy).
- `serve --in-memory` keeps storage off disk, discards it at shutdown, and defaults to 64 MiB of committed and staged payloads (`--memory-limit` in bytes). Page and append blobs count the bytes of their extents, not their logical length, so a sparse 8 TiB page blob costs nothing until written.
- Per-request limits, all in bytes: `--max-blob-bytes` for a single Put Blob request (default 256 MiB, up to 5000 MiB), `--max-block-bytes` for Put Block (default 5000 MiB), and `--max-assembled-blob-bytes` for a committed block blob (default 512 MiB).
- `--port`, `--admin-port`, and `--bind` select the listeners. Use `--config` for a TOML file; flags override `AZUIFER_*` environment values, then file values, then defaults. Run `cargo run --locked -- config validate` with the same options to validate settings.
- `--skip-api-version-check` is described under Authentication. Omit it for strict mode, or use `--skip-api-version-check=false` to override a setting from the environment or file.
- `--upload-timeout-seconds` bounds time spent receiving a single upload body (1 to 600 seconds; default 60). An incomplete timed-out upload does not replace an existing Blob. `serve --shutdown-on-stdin-eof` lets a process supervisor close a piped stdin to shut the listeners down gracefully.
- `--test-clock` ([ADR-0012](../adr.d/0012-inject-time-through-one-clock.md)) is refused with a non-loopback bind. It adds `GET /_azuifer/clock` and `POST /_azuifer/clock/advance?seconds=N` (or `ms=N`) to the admin listener, and keeps them on the Blob listener for existing tests. Both act on the one clock the Blob, Queue, Table, Files and DFS services share, so tests can expire leases, queue visibility and TTLs, SAS tokens, and policies without sleeping. Signed requests still carry the real date unless the client reads the clock, so keep the total shift under the 15 minute skew window when using Shared Key (DFS checks request dates against the real time).
- A TOML file can use `[[accounts]]` entries with `name` and a `keys` array containing one or two Base64 Shared Keys. Keep such files out of version control. `AZUIFER_ACCOUNT_KEY` overrides the keys for `AZUIFER_ACCOUNT_NAME` (defaults to `devstoreaccount1` if omitted).

Blob names are case-sensitive database keys, not filenames. The [HTTP suite](../../tests/blob_http.rs) checks case and Unicode distinctions across restart, including names reserved by Windows filesystems, and opens a data directory with spaces. Use a private local data path on each host rather than sharing a live SQLite directory across hosts.

## AzCopy

AzCopy 10.34.2 (Windows amd64) was run against a debug build with `serve --in-memory --memory-limit 4294967296 --skip-api-version-check --services blob,file,dfs`. AzCopy cannot sign with an account key, so every command used an account or container SAS made with `azure-storage-blob` and the public `devstoreaccount1` key (loopback only). The scenarios that pass:

- `copy` up of one file, of a directory tree (many small files and a 300 MiB file, so block uploads run in parallel), and with `--put-md5`, `--metadata`, `--blob-tags`, `--block-blob-tier`, content headers, and `--blob-type PageBlob` or `AppendBlob` (including a sparse 20 MiB page blob); `copy` down with `--check-md5 FailIfDifferent` (and its rejection of a wrong `Content-MD5`), each compared by SHA-256.
- `list` with `--properties`, `sync` in both directions (nothing is re-sent when unchanged; changed, new, and `--delete-destination` files are), `--compare-hash MD5`, `remove --recursive`, container and account SAS, names with spaces, `+`, `#`, `&`, `%`, Unicode, and empty files.
- `copy --from-to BlobBlob` inside one account (Put Block From URL, Put Blob From URL, Put Page From URL, Append Block From URL), with and without `--s2s-preserve-properties`.
- Killing a throttled upload and finishing it with `jobs resume <id> --destination-sas`.

Limits you meet when using AzCopy against Azuifer:

- AzCopy does not recognise a bare IP endpoint, so pass `--from-to` (`LocalBlob`, `BlobLocal`, `BlobBlob`, `BlobTrash`) to `copy`, `sync` and `remove`, and `--location Blob` to `list`. `azcopy make` has no such flag and rejects `http://127.0.0.1:10000/…`; use the host-style URL `http://devstoreaccount1.blob.localhost:10000/{container}?{sas}` (it worked here), or create the container with any other client. AzCopy never creates a missing container.
- AzCopy opens up to 256 connections, but 16 requests are active at a time. A request waits up to 5 seconds for a slot before it is answered `503 ServerBusy`, which AzCopy retries; under heavy load the log still shows some. The in-memory default of 64 MiB of payload is too small for large transfers: raise `--memory-limit`.
- `azcopy make` and `--from-to` pairs involving Files, and Blob to Files copies, are covered in [files.md](files.md#azcopy). Blob to Files and Files to Blob server-side copies fail because the two services keep separate stores and Azuifer makes no outbound requests, so download to disk first.

`tests/azcopy_smoke.py` runs a compact version of this against a running server and prints `PASS` or `FAIL` for each of 30 steps, Blob and Files together:

```sh
azuifer serve --in-memory --memory-limit 1073741824 --skip-api-version-check --services blob,file
python tests/azcopy_smoke.py --azcopy /path/to/azcopy        # pip install azure-storage-blob azure-storage-file-share
```

It downloads nothing and keeps AzCopy's logs and job plans in a temporary directory (AzCopy still writes `~/.azcopy/installation_id` and a `pids` folder). It takes `--blob-url`, `--file-url`, `--blob-sas` and `--file-sas` to use your own endpoints and tokens. A pass shows that this AzCopy version completes those workflows with the expected bytes, MD5s and sync decisions; it does not show wire equivalence with Azure Storage. [`tests/azcopy_regressions_http.rs`](../../tests/azcopy_regressions_http.rs) pins each defect AzCopy found as an HTTP test.

## Container

Follow the [Docker quickstart](../../README.md#run-locally) to build the [Azure Linux image](../../Dockerfile) and try it with Azure CLI. The explicit in-container bind allows port forwarding while the published host ports stay loopback-only.
